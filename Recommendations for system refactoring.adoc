= Рекомендации по предварительному рефакторингу системы до внедрения доработок

Перед внедрением архитектурных изменений, предусмотренных проектной работой, рекомендуется выполнить предварительный рефакторинг существующей системы. Его цель — снизить технический долг, уменьшить связанность компонентов и подготовить систему к переходу на событийно-ориентированную архитектуру с использованием RabbitMQ, Transactional Outbox и Интеграционного сервиса.

Предварительный рефакторинг рекомендуется выполнять поэтапно, не изменяя сразу бизнес-функциональность системы.

== 1. Разделить бизнес-логику и интеграционную логику

В существующем Backend API необходимо исключить прямые вызовы внешних информационных систем из бизнес-компонентов.

Следует придерживаться принципа:
Controller -> Business Component -> Repository

а интеграционные операции передать в отдельный Интеграционный сервис.

Это позволит отделить бизнес-логику создания продукта от логики взаимодействия с внешними системами.

== 2. Выделить единый Repository Layer

Необходимо проверить существующие компоненты и исключить прямой доступ различных компонентов к PostgreSQL.

Доступ к данным должен осуществляться через специализированные репозитории:
Product Management -> Product Repository -> PostgreSQL

При этом компонент, отвечающий за работу с событиями, не должен самостоятельно выполнять бизнес-операции с продуктами.

Это снизит связанность компонентов и упростит дальнейшее внедрение Transactional Outbox.

== 3. Унифицировать модели данных

До внедрения событийного обмена рекомендуется определить единые модели:

* Product;
* Recipe;
* Ingredient;
* Approval;
* ProductStatus;
* DomainEvent;
* IntegrationTask.

Для каждой сущности необходимо определить обязательные поля, идентификаторы и правила изменения состояния.

Особенно важно заранее определить стабильный Product ID, который будет использоваться при передаче информации между всеми системами.

== 4. Ввести единый жизненный цикл продукта

Рекомендуется формализовать состояния продукта, например:
DRAFT -> IN_REVIEW -> APPROVED -> PUBLISHED

При необходимости должны быть предусмотрены состояния:

* REJECTED
* CANCELLED

Переходы между состояниями должны выполняться централизованно, а не изменяться произвольными компонентами.

Это позволит в дальнейшем однозначно формировать события:

* ProductCreated
* RecipeUpdated
* ProductApproved
* ProductPublished

== 5. Подготовить систему к Transactional Outbox

До внедрения RabbitMQ рекомендуется подготовить структуру базы данных для хранения событий.

Сохранение бизнес-данных и Outbox-события должно выполняться в рамках одной транзакции:

BEGIN TRANSACTION -> Сохранить Product + Создать OutboxEvent -> COMMIT

После этого отдельный Event Publisher Worker будет отвечать за публикацию событий в RabbitMQ.

== 6. Убрать синхронную зависимость от внешних систем

До реализации целевой архитектуры следует выявить все места, где Backend API непосредственно ожидает ответа от внешних систем.

Если внешний вызов не требуется для непосредственного формирования ответа пользователю, его рекомендуется сделать асинхронным.

== 7. Ввести идемпотентность

Перед переходом на асинхронную доставку необходимо подготовить внешние интеграции к повторной обработке сообщений.

Внешняя система не должна в результате создать два одинаковых продукта.

Для этого необходимо использовать:

* event_id;
* product_id;
* идентификатор операции;
* проверку уже обработанных сообщений.

== 8. Стандартизировать обработку ошибок

До внедрения новых интеграций рекомендуется определить единый подход к ошибкам:

* 4xx → ошибка запроса/данных
* 5xx → ошибка внешней системы
* timeout → повторная попытка
* connection error → повторная попытка
* validation error → без повторной попытки

Это позволит корректно настроить Retry в Delivery Worker.

Для ошибок, которые невозможно исправить автоматически, следует использовать Dead Letter Queue.

== 9. Ввести Correlation ID

До масштабирования системы рекомендуется добавить единый идентификатор операции: Correlation-ID

Он должен передаваться через весь путь обработки:

API Gateway -> Backend API -> Outbox -> RabbitMQ -> Интеграционный сервис -> Delivery Worker -> Внешние системы

Это значительно упростит поиск ошибок и анализ цепочки выполнения одной операции.

== 10. Подготовить единое логирование

Перед внедрением распределенной архитектуры необходимо стандартизировать формат логов.

Рекомендуется фиксировать как минимум:

* временная метка;
* сервис;
* компоненты ;
* correlation_id;
* user_id;
* event_id;
* product_id;
* операции;
* статус;
* код ошибки.

При этом в логах не должны храниться пароли, JWT-токены и другие чувствительные данные.

== 11. Проверить API и контракты интеграции

Перед созданием Интеграционного сервиса необходимо провести аудит существующих API.

Для каждого внешнего сервиса следует определить:

* URL;
* HTTP-метод;
* формат запроса;
* формат ответа;
* обязательные поля;
* коды ошибок;
* timeout;
* требования к аутентификации;
* допустимое количество повторных запросов;
* требования к идемпотентности.

Результатом должен стать единый каталог интеграций.

== 12. Подготовить мониторинг

До перехода на асинхронную архитектуру необходимо определить метрики, которые будут контролироваться после внедрения:

* количество сообщений в RabbitMQ;
* количество необработанных Outbox-событий;
* количество повторных попыток;
* количество ошибок доставки;
* размер DLQ;
* latency API;
* latency интеграций;
* количество активных Worker;
* состояние PostgreSQL.

Это позволит контролировать выполнение НФТ по производительности, доступности и надежности.
