= Рекомендации команде разработки по внедрению процесса документирования

Для проекта рекомендуется внедрить единый процесс архитектурного и технического документирования. Документация должна создаваться и актуализироваться одновременно с разработкой, а не после завершения работ. Это особенно важно для Платформы управления внедрением новых продуктов, поскольку система взаимодействует с большим количеством внешних ИТ-систем и использует асинхронные механизмы обмена.

== 1. Создать единый репозиторий документации

Все проектные документы рекомендуется хранить в едином контролируемом репозитории, связанном с Git-репозиторием исходного кода.

== 2. Ввести обязательный набор архитектурных диаграмм

Для Платформы управления внедрением новых продуктов рекомендуется поддерживать следующие уровни C4:

* C1 — контекстная диаграмма;
* C2 — диаграмма контейнеров;
* C3 — диаграмма компонентов;
* C4 — диаграмма кода для наиболее сложных компонентов (при необходимости).

Диаграммы должны обновляться при изменении архитектуры.

== 3. Использовать Architecture Decision Records (ADR)

Все существенные архитектурные решения необходимо фиксировать в формате ADR.

Каждый ADR должен содержать:

* проблему;
* контекст;
* рассматриваемые варианты;
* принятое решение;
* последствия;
* дату;
* автора;
* статус решения.

Это позволит в дальнейшем понять не только что было реализовано, но и почему было принято именно такое решение.

== 4. Документировать API

Для всех REST API необходимо использовать единый стандарт документирования, например OpenAPI/Swagger.

Для каждого endpoint необходимо описывать:

* назначение;
* HTTP-метод;
* URL;
* параметры;
* структуру запроса;
* структуру ответа;
* коды ошибок;
* требования к авторизации;
* примеры запросов и ответов.

Документация API должна обновляться вместе с изменением API.

== 5. Документировать интеграции

Для каждого взаимодействия Интеграционного сервиса с внешней системой рекомендуется создавать отдельное описание.

Описание должно включать:

* назначение интеграции;
* источник данных;
* получатель данных;
* протокол;
* формат данных;
* метод аутентификации;
* timeout;
* retry;
* идемпотентность;
* возможные ошибки;
* порядок повторной доставки.

== 6. Ввести каталог событий

Поскольку Платформа управления внедрением новых продуктов использует EDA, необходимо вести каталог событий.

Для каждого события следует фиксировать версию схемы и правила обратной совместимости.

== 7. Документировать Transactional Outbox

Для Outbox необходимо описать:

* структуру таблицы;
* жизненный цикл события;
* статусы;
* количество попыток;
* правила публикации;
* обработку ошибок;
* правила очистки старых записей.

== 8. Вести реестр НФТ

Все нефункциональные требования необходимо хранить в едином реестре.

Это позволит связать требования с конкретными архитектурными решениями и тестами.

== 9. Документировать требования безопасности

В соответствии с выбранным подходом ISO/IEC 27001 необходимо вести отдельный раздел.

В нем следует фиксировать:

* требования к аутентификации;
* требования к авторизации;
* роли и права;
* защищаемые объекты;
* правила хранения данных;
* требования к TLS;
* требования к журналированию;
* правила обработки инцидентов;
* требования к резервному копированию;
* результаты проверок безопасности.

== 10. Ввести правила актуализации документации

Для каждого документа необходимо определить ответственного.

Документ считается актуальным только после прохождения review.

== 11. Включить документацию в Definition of Done

Изменение не должно считаться полностью выполненным, пока не обновлена соответствующая документация.

Это позволит избежать накопления технического и документационного долга.

== 12. Проводить регулярное Review по документации

Рекомендуется проводить проверку документации:

* при каждом значимом архитектурном изменении;
* перед релизом;
* после изменения интеграционных контрактов;
* после изменения НФТ;
* после архитектурного решения, влияющего на безопасность.

Дополнительно один раз за итерацию можно проводить короткий аудит актуальности документации.

== 13. Использовать версионирование документации

Документация должна изменяться вместе с кодом и иметь историю изменений.

Для API и событий особенно важно хранить версии.

При несовместимых изменениях старая версия должна поддерживаться в течение согласованного периода миграции.

== 14. Связать документацию с задачами разработки

Каждая значимая задача должна иметь ссылки на соответствующие документы.

Это обеспечивает трассируемость от требования до реализации.

== 15. Документировать эксплуатацию

Для Production необходимо создать эксплуатационную документацию:

* порядок запуска;
* порядок остановки;
* мониторинг;
* резервное копирование;
* восстановление;
* процедуры при отказе RabbitMQ;
* процедуры при отказе PostgreSQL;
* обработка DLQ;
* масштабирование Worker;
* контакты ответственных команд.

Особенно важно документировать процедуры восстановления с учетом заявленных RTO = 1 час и RPO = 15 минут.
